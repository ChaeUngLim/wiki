Gajae-Code(gjc): 계획 먼저, 증거로 끝내는 가벼운 랄프톤 하네스

가볍다 = 기본 기능이 적고(스킬 4개 + 역할 4개) 흐름이 하나라는 뜻이다. 작업 시간을 뜻하지 않는다.

왕초보 설명

  • 이게 뭐야? gjc(가재코드)는 터미널에서 쓰는 AI 코딩 도우미다. “이거 고쳐줘”라고 하면 코드를 읽고, 계획하고, 고치고, 제대로 됐는지 확인까지 한다. Claude, ChatGPT, Gemini 같은 AI를 이미 내고 있는 월 구독으로 연결해 쓴다.
  • 하네스로서 특징은? “바로 고치지 말고 먼저 묻고, 계획하고, 검토받은 다음 고친다.” 그리고 “다 했어요”를 말이 아니라 증거 기록으로 끝낸다.
  • 랄프톤이 뭐야? 랄프톤(Ralph-thon)은 “Ralph 루프”를 쓰는 해커톤을 부르는 말이다. Ralph 루프는 AI에게 목표를 주고 끝날 때까지 스스로 반복(만들기 → 확인 → 고치기)하게 하는 방식이다. gjc에는 ralph라는 명령이 없다. 대신 deep-interview → ralplan → ultragoal 세 단계와 자동 넘김 설정으로 같은 일을 한다.
  • 나는 뭘 하면 돼? 처음엔 아래 세 줄만 기억하면 된다.
  • 주의: 실행 단계(ultragoal)는 git 커밋 기록으로 “무엇이 바뀌었는지”를 계산한다. git을 쓰지 않거나 커밋이 하나도 없는 폴더에서는 목표를 “완료”로 기록하지 못하고 막힌다. 오래 돌릴 때는 gjc --tmux --worktree 작업이름으로 원본과 분리된 폴더에서 돌린다.

단계별로 조금 더

① deep-interview — 질문으로 요구 정리

  • 질문을 하나씩 하고, 답할 때마다 요구가 얼마나 흐릿한지 “모호함 점수”를 매긴다. 점수가 기준(threshold) 아래로 내려가면 명세를 쓴다.
  • 기준값: 기본 0.05(5%). --quick 0.6, --standard 0.5, --deep 0.35. 첫 줄에 Deep Interview threshold: …를 출력해 어떤 기준으로 도는지 보여 준다.
  • 명세에는 목표, 제약, 하지 않을 것(Non-Goals), 완료 기준(Acceptance Criteria), 인터뷰 기록이 들어간다.

② ralplan — 세 역할이 합의할 때까지 계획

  • PLANNER가 계획과 요약(원칙 3~5개, 결정 요인 3개, 선택지 2개 이상)을 쓰고, ARCHITECT와 CRITIC이 검토한다(일하는 쪽과 확인하는 쪽 분리). CRITIC은 “실행 가능하고 검증 가능한 계획만 승인”하는 읽기 전용 역할이다.
  • 합의가 안 되면 고쳐서 다시 검토한다. gjc.ralplan.maxIterations(기본 5)를 넘으면 PLANNING-STUCK로 멈추고, 자동 넘김이 켜져 있어도 실행하지 않는다.
  • 계획 기록은 gjc ralplan --write로만 저장된다. 계획 단계에서는 제품 코드 수정, 커밋, 푸시가 코드로 막혀 있다.

승인 게이트 — 반자동 vs 완전 자동 (raw/gjc-beginner-guide.html 7장)

③ ultragoal — 목표별로 끝까지 실행하고 증거 남기기

  • 승인된 계획을 @goal: 줄로 나눠 목표 G001, G002 …를 만든다. 검증이 서로 묶인 이야기(같은 기능 묶음, 같은 완료 기준)는 한 목표로 합치고, 그 안에서 executor를 여러 개 나눠 돌린다.
  • 목표 하나가 끝날 때마다 gjc ultragoal checkpoint --status complete --evidence "…" --quality-gate-json …로 무슨 검증을 돌렸고 통과했는지를 기록한다. 변경 파일 목록과 해시(changeSetHash)는 git diff에서 자동 계산된다.
  • 중간 목표는 가벼운 검증만 하고, 마지막 목표(경계)에서 한 번 무거운 검토를 한다: 코드 정리, architect 구조 리뷰, executor QA를 같은 스냅숏에 동시에 돌리고 결과를 합친다.
  • 끝낼 때(완료든 일시정지든) 읽기 전용 critic의 OKAY가 있어야 한다.
  • 막혔을 때: AI가 해결할 수 있는 문제(resolvable: 테스트 실패, 설치 누락 등)면 멈추지 않고 계속 시도한다. 사람만 풀 수 있는 문제(human_blocked: 비밀번호, 결제, 승인)일 때만 일시정지할 수 있다. 실행 중에는 질문(ask)도 막혀 있어서, 결정할 일은 막힘 기록으로 남긴다.
  • 끈기: gjc.ultragoal.nudgeBudget(기본 10)은 목표 하나에서 포기하기 전까지 다시 밀어붙이는 횟수다. “goal 모드”(goal.enabled)가 켜져 있어야 턴이 끝나도 다음 작업으로 이어진다.

(선택) autoresearch — 조사 전용

코드를 만들지 않고, 웹 검색과 데이터 실험으로 질문 하나에 대한 결론(status, evidence[], caveats[])을 낸다. 보통 deep-interview 다음, ralplan 전에 넣는다.

계보

  • 원문(NOTICE.md)상 gjc는 oh-my-pi를 “윗줄 계보와 구현 DNA”로 삼고, oh-my-codex와 oh-my-claudecode의 워크플로 실험에서 배운 것을 이어받았다. 그래서 스킬 이름(deep-interview, ralplan, ultragoal)이 oh-my-claudecode와 겹치고, 각 SKILL.md에 “forked from upstream … rebranded for GJC”라고 적혀 있다.
  • 코스의 pi 분석 대상(badlogic/pi-mono)과 oh-my-pi는 이름이 비슷하지만, 둘의 관계는 이 위키가 가진 원문(NOTICE.md, 코스 Pi 분석)으로는 확인되지 않는다. 설계 면에서는 둘 다 작은 기본 구성에 스킬·확장을 얹는 쪽이고, gjc는 그 위에 계획·실행 워크플로 4개를 기본으로 묶었다.

장점 (왕초보 관점)

  1. 배울 게 적다. 기억할 흐름이 deep-interview → ralplan → ultragoal 하나다. 스킬이 4개뿐이라 “지금 뭐가 돌고 있지?”를 헷갈릴 일이 적다.
  2. 안전하다. 계획이 끝나고 승인하기 전에는 코드가 바뀌지 않는다. 계획이 막히면(PLANNING-STUCK) 자동 실행 설정이 켜져 있어도 실행하지 않는다.
  3. 돈을 두 번 내지 않는다. 이미 내는 월 구독으로 돌린다. 한 회사 구독이 바닥나도 다른 회사 모델로 역할을 나눌 수 있다.
  4. “다 했어요”를 믿을 수 있다. 완료는 AI의 말이 아니라 목표별 검증 기록과 마지막 critic의 OKAY로 정해진다.
  5. 끝없이 돌지 않는다. 목표 하나당 다시 밀어붙이는 횟수가 nudgeBudget(기본 10)으로 정해져 있어 한도를 다 태우는 사고가 적다.
  6. 자리를 비워도 된다. --tmux로 창을 닫아도 돌고, 막히면 폰으로 알림이 온다.

단점과 주의할 점

  1. git이 사실상 필수다. ultragoal은 변경 범위를 git diff로 계산한다. git을 안 쓰거나 커밋이 하나도 없는 폴더에서는 목표를 “완료”로 기록하지 못한다. 시작 전에 git init과 첫 커밋을 해 둔다.
  2. 처음 설정이 길다. 로그인, 역할별 모델, 자동 넘김(gjc.ralplan.autoHandoff), goal 모드, 알림을 하나씩 맞춰야 한다. 왕초보 가이드가 13장짜리인 이유다.
  3. 실행 중에는 AI가 질문하지 않는다. ultragoal이 도는 동안 질문(ask)이 막혀 있다. 애매한 건 “막힘 기록”으로 남기고 계속 간다. 그래서 인터뷰 단계에서 충분히 답해 둬야 한다.
  4. 베타다. README가 직접 “거친 부분이 있을 수 있다”고 쓴다. 중요한 작업은 결과를 직접 확인한다.
  5. 문서의 버전 함정. README 설치 예시가 v0.15.3에 고정돼 있다. 그대로 설치하면 최신 모델이 없어 오류가 날 수 있다(가이드 2장). 설치 후 gjc update.
  6. 다른 AI CLI를 팀으로 부리는 기능은 번들에 없다. 목표 안에서 executor를 여러 개 나눠 돌리는 병렬화는 있지만, OMC의 omc team 2:codex처럼 다른 회사 CLI를 tmux 창마다 띄우는 모드는 없다.
